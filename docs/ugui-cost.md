# uGUI 캔버스 비용 — 실측

연출 자체의 비용과 **연출이 건드린 결과로 캔버스가 다시 만들어지는 비용**은 다르다.
후자가 대개 훨씬 크고, 이 패키지가 아니라 uGUI의 성질이다. 어떤 연출 시스템을 쓰든
같으므로 여기서는 그 값을 재서 남긴다.

## 측정 조건

Unity 6000.5.3f1 · Apple Silicon · batchmode PlayMode · 조건당 180프레임 평균.
`ProfilerRecorder`로 아래 마커를 잡았다.

- `UIEvents.WillRenderCanvases` — 매니지드 리빌드. Graphic의 메시를 다시 만든다
- `Canvas.BuildBatch` — 네이티브 배칭. 캔버스의 렌더러를 다시 합친다

재현 하네스는 `docs/ugui-cost-harness~/`에 있다. 폴더 이름이 `~`로 끝나는 것은 의도다 —
Unity는 그런 폴더를 임포트하지 않으므로, 이 패키지를 쓰는 프로젝트에 시험용 어셈블리가
딸려 들어가지 않는다.

## 결과

| 시나리오 | 리빌드 | BuildBatch |
|---|---|---|
| 기준 120칸 (아무것도 안 바꿈) | 0.91 µs | **0** |
| 120칸 / **1개** 스케일 | 11.86 µs | 7.67 µs |
| 120칸 / **30개** 스케일 | 13.28 µs | 6.71 µs |
| 30칸 / 1개 스케일 | 11.34 µs | 7.25 µs |
| 600칸 / 1개 스케일 | 15.64 µs | 10.95 µs |
| 600칸 / 30개 스케일 | 17.42 µs | 10.47 µs |
| 120칸 / **CanvasGroup.alpha** | **9.85 µs** | 6.76 µs |
| 120칸 / `Graphic.color` 1개 | 11.91 µs | 6.48 µs |
| 120칸 / **`Graphic.color` 30개** | **98.25 µs** | 6.84 µs |
| 600칸 / 30개를 **자식 Canvas로** | 13.25 µs | 6.10 µs |

## 읽는 법

### 1. 비용을 정하는 것은 "몇 개가 바뀌었나"가 아니라 "캔버스가 더러워졌나"다

1개를 스케일하는 것과 30개를 스케일하는 것이 **12퍼센트** 차이다(11.86 → 13.28).
반면 캔버스를 120칸에서 600칸으로 키우면 같은 1개를 움직여도 **38퍼센트** 는다
(11.86 → 15.64).

트랜스폼이 하나라도 바뀌면 그 캔버스 전체가 다시 만들어지기 때문이다. 그래서 대응은
"연출을 줄인다"가 아니라 "캔버스를 쪼갠다"이다.

아무것도 바뀌지 않으면 `BuildBatch`가 정확히 0이다 — 더티 모델이 실제로 그렇게 돈다.

### 2. `Graphic.color`만 개수에 비례해 는다

| 바꾼 개수 | `Graphic.color` | `CanvasGroup.alpha` |
|---|---|---|
| 1개 | 11.91 µs | — |
| 30개 | **98.25 µs** | 9.85 µs |

`Graphic.color`는 그 Graphic의 메시를 다시 만들게 한다. 그 비용이 바꾼 개수만큼 쌓인다.
`CanvasGroup.alpha`는 배칭 단계에서 곱해질 뿐이라 메시를 만들지 않는다 —
**스케일보다도 싸다.**

> 흔한 오해: "CanvasGroup은 정점 색을 바꾸니 비싸다." 측정은 반대다.

### 3. CanvasGroup과 자식 Canvas는 다른 문제를 푼다

| 문제 | 도구 | 근거 |
|---|---|---|
| 여러 개를 페이드해야 한다 | **CanvasGroup** | 98.25 → 9.85 µs |
| 자주 움직이는 것이 큰 캔버스를 더럽힌다 | **자식 Canvas** | 17.42 → 13.25 µs, BuildBatch 10.47 → 6.10 µs |

`CanvasGroup`은 배치를 나누지 않는다. 배치 단위를 나누는 것은 자식 `Canvas` 컴포넌트다.

자식 Canvas를 남발하면 배치가 잘게 쪼개져 드로우콜이 는다. 요소마다가 아니라
**같은 리듬으로 바뀌는 덩어리** 단위로 뗀다.

## 이 패키지의 노드는 어디에 해당하나

| 노드 | 만지는 것 | 비용 |
|---|---|---|
| `Scale` · `Move` · `Rotate` · `Float` · `Bounce` · `FlyAcross` | 트랜스폼 | 캔버스 크기에 따라 완만. 개수에 거의 무관 |
| `Fade` — `CanvasGroup` 경로 | `CanvasGroup.alpha` | **가장 쌈** |
| `Fade` — `Graphic` 폴백 | `Graphic.color` | 개수에 비례. 30개면 8배 |
| `Color` | `Graphic.color` | 위와 같음 |

`Fade`는 대상에 `CanvasGroup`이 있으면 그것을, 없으면 `Graphic`을 쓴다. **CanvasGroup을
하나 빼먹은 것만으로 싼 경로가 비싼 경로가 된다.** 그래서 폴백이 일어나고 그 대상 아래에
다른 Graphic이 더 있으면 경고한다 — 그때는 비용뿐 아니라 **보이는 결과도 다르다**(대상
자신만 흐려지고 자식은 또렷하게 남는다).

Graphic 하나짜리 페이드에는 경고하지 않는다. 정당한 쓰임이고 비용도 트랜스폼과 같다.

## 단서

- **batchmode다.** 실제 프레젠테이션 일부가 빠졌을 수 있다. 다만 결론을 좌우하는 리빌드
  수치는 매니지드 경로라 영향받지 않는다.
- **데스크톱이다.** 기기(IL2CPP·모바일)에서는 절대값이 몇 배 커진다. 상대 순위는 그대로다.
- **Unity 6의 uGUI 배칭은 잡 기반이다**(`PrepareBatchesJob`·`GeometryJob`·`SortJob`).
  예전 Unity에서 잰 수치와 직접 비교하지 말 것.
- 절대값을 그대로 믿기보다, 자기 프로젝트에서 같은 마커를 프로파일러로 보는 것이 맞다.
  여기서 가져갈 것은 **순위와 스케일 법칙**이다.
